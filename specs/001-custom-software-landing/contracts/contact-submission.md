# External Contract: Contact Submission

## Purpose

Define the provider-neutral browser contract for sending a minimal callback request to the company
email without coupling the Astro UI to a vendor SDK or operating a bespoke application backend.

## Configuration boundary

- The static build receives one public HTTPS endpoint URL from validated build configuration.
- The browser bundle contains no provider secret, private token, mailbox credential, or privileged
  identifier.
- If a provider requires a secret, a managed form service or serverless endpoint holds it on its
  trusted boundary.
- Production accepts requests only from approved site origins and HTTPS.

## Request

**Method**: `POST`

**Content type**: `application/json` for enhanced submission. A selected provider should also accept
`application/x-www-form-urlencoded` or an equivalent native-form fallback without changing field
semantics.

| Field | Type | Required | Rule |
|---|---|---:|---|
| `name` | string | yes | Trimmed, 2-80 characters |
| `preferredChannel` | string | yes | `call`, `whatsapp`, or `email` |
| `phone` | string | conditional | Required only for `call` or `whatsapp` |
| `email` | string | conditional | Required only for `email` |
| `consent` | boolean | yes | Must equal `true` |
| `privacyVersion` | string | yes | Active notice version in `YYYY-MM-DD` format |
| `source` | string | yes | Stable value `landing-custom-software` |
| `website` | string | no | Honeypot; legitimate value is empty |

The endpoint treats an empty inactive contact field as absent, discards unknown fields, and rejects
requests containing two non-empty contact fields or a field that does not match the selected channel.
The decoded payload must not exceed 8 KiB.

## Success response

**Status**: `200 OK` or `202 Accepted`

```json
{
  "success": true,
  "requestId": "opaque-id",
  "receivedAt": "2026-09-08T15:30:00Z"
}
```

- `requestId` is required and must not encode personal data.
- `receivedAt` is generated by the trusted endpoint and is authoritative for delivery and response
  timing; browser-provided time is ignored.
- Success means the endpoint accepted responsibility for delivering the request to the company
  email; it does not claim the company has already contacted the person.
- The UI announces success and the 1-business-day response commitment.
- The provider must expose delivery status, bounded retries, and a terminal-failure alert so browser
  acceptance and actual email delivery can be verified separately.

## Validation response

**Status**: `400 Bad Request` or `422 Unprocessable Content`

```json
{
  "success": false,
  "code": "validation_error",
  "fieldErrors": {
    "email": "Ingresá un correo válido."
  }
}
```

Allowed keys in `fieldErrors` are `name`, `preferredChannel`, `phone`, `email`, and `consent`.
Messages shown to users are Spanish, specific, and do not reveal validation internals.

An inactive or unknown `privacyVersion` returns `409 Conflict` with
`{"success":false,"code":"privacy_notice_outdated"}`. The UI asks the visitor to reload, read the
current notice, and consent again; it must not silently resubmit.

## Abuse response

**Status**: `429 Too Many Requests`

```json
{
  "success": false,
  "code": "rate_limited"
}
```

The endpoint applies a documented provider-specific quota, honeypot evaluation, the 8 KiB payload
limit, and safe origin checks. A `429` response includes `Retry-After`; oversized payloads return
`413`, and rejected production origins return `403`. Origin/CORS checks are defense in depth, not
authentication or a substitute for abuse controls. The client times out after 10 seconds. The UI
uses a neutral retry-later message and the company email fallback. No visual CAPTCHA that creates an
accessibility barrier is accepted.

## Service failure

**Status**: `5xx`, timeout, offline condition, invalid JSON, or network failure

- The UI must not show success.
- Preserve name, selected channel, and contact value for retry in the current page only.
- Announce the failure without moving focus unexpectedly.
- Offer the public company email as an alternative.
- Do not log the payload or personal data to browser analytics or error reporting.

## No-JavaScript baseline

When JavaScript is unavailable, the landing content, navigation, services, projects, privacy link,
and direct company-email link remain usable. The multi-channel enhanced form does not claim to work;
a `noscript` notice explains how to contact the company by email. The confirmation route remains
available for endpoint/provider redirects but is never used to imply delivery without acceptance.

## Email delivery contract

The delivered company email includes the sender name, selected channel, matching contact value,
consent version, authoritative `receivedAt`, request ID, and source. It excludes inactive fields and
the honeypot. The company attempts contact by the chosen channel before the end of the next business
day in `America/Argentina/Buenos_Aires`; business days are Monday-Friday excluding Argentine national
holidays. The email workflow records qualification/conversion and deletes non-client prospect data no
later than 90 days after the last contact. Direct emails to the fallback address follow the same rule.
Deletion retains only non-personal audit events.

## Provider acceptance checklist

- Supports the request and response semantics above without a vendor UI component.
- Provides HTTPS, origin controls, server-side validation, abuse protection, and delivery monitoring.
- Does not expose credentials in the static site.
- Identifies the processor, processing location, subprocessors, international transfers, deletion
  controls, incident terms, and any required data-processing agreement for the Argentine audience.
- Supports data deletion and the 90-day non-client retention workflow.
- Allows the privacy notice to identify the controller and contact, purpose, lawful basis, fields,
  recipients, retention, transfers, rights procedure, and notice version. Legal text is reviewed by
  a qualified person before any compliance claim is published.
- Can be replaced by changing configuration and a thin adapter, not section markup.
